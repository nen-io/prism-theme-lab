# Accessibility and everyday use

Prism lets you edit a palette, inspect the actual preview and repair measured contrast pairs. Pick a preset, change a color, follow a failing pair to its exact field, then undo or export. The studio shell uses stable colors even when the preview deliberately fails contrast.

## Navigation and keyboard model

- The first Tab reveals **Skip to workbench**. Activating it focuses the actual editor section, bypassing the hero and presets; the next Tab reaches **Theme name**.
- All colors have labelled hex fields alongside native color pickers. Type a six-digit hex value and press Enter or leave the field to commit. Escape restores the committed value. Picker behavior itself is provided by the browser/OS.
- Theme names use the same domain validator on import and edit. An invalid draft remains in the field, receives `aria-invalid` and its own associated explanation, and never enters history or export. Escape restores the saved name; newer draft intent still fences pending file imports.
- The visible **Import JSON** button opens the file chooser. Its underlying hidden input is not an extra invisible Tab stop.
- Contrast-pair actions focus the relevant hex field. Suggested repairs describe the affected measured pairs and stay undoable. Mode buttons expose their selected state; preview text scaling has a spoken percent value.
- The sample project form announces creation as preview-only, keeps the entered result visible, and focuses its input if an empty value is submitted. The preview does not create a remote account or project.

## Layout and visual states

Essential editor controls and help use larger type, hex fields and history controls have larger hit areas, and coarse-pointer controls expand to 44px. At 320px the workbench becomes a single column. CSS output remains a separately scrollable, focusable region. Forced-colors styles preserve focus and selected-control boundaries. Preview colors remain user-controlled: overriding them would hide precisely the contrast failure the tool is meant to demonstrate.

The hero heading can break a long word when enlarged so it does not widen the page. Hex token keys wrap below the value when the two no longer fit side by side. The skip link is clipped while unfocused instead of relying on a fixed negative offset, so scrolling and enlarged text cannot expose a stray overlay.

## Verification

`tests/e2e/accessibility.spec.ts` checks the first keyboard skip path, editor focus, hidden file input, invalid-name description and Escape repair, preview feedback, 320px layout, enlarged control text, forced colors and a usable manual hex alternative. Existing tests verify direct contrast repair, token-to-rendered-preview agreement, import races, undo and full workspace roundtrips. [Actual desktop](screenshots/desktop.png) and [mobile screenshots](screenshots/mobile.png) are regenerated by the full suite; [TESTING.md](TESTING.md) records commands and evidence limits.

The narrow text-size regression captures computed font sizes before doubling headings, controls, labels and supporting text together. It includes the visible invalid-name error, Escape recovery and a keyboard hex edit. This caught a 349px page width at a 320px viewport that the previous control-only check missed. The [forced-colors capture](screenshots/accessibility-forced-colors.png) shows the actual focused editor after repair; emulation remains distinct from physical assistive-technology testing.

## Decisions and limits

Native controls provide familiar interaction instead of a custom color-picker widget. Field-level validation separates a visible invalid draft from the valid exported model, without inventing a second validation rule. Focus moves only in response to explicit navigation or repair. There is no new dependency, unbounded history, remote processing or storage schema change.

Passing the four color pairs does not certify a palette or application as accessible. Deliberately failing custom themes are expected; their failures are part of the result. VoiceOver/NVDA, switch control, OS picker behavior on physical mobile devices and user research with disabled participants have not been tested. Automated rules, DOM descriptions and emulation do not establish assistive-technology compatibility or WCAG conformance.

Guidance reviewed 23 September 2026: [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [WAI form notifications](https://www.w3.org/WAI/tutorials/forms/notifications/), [Playwright accessibility testing limits](https://playwright.dev/docs/accessibility-testing).

## Additional production-engine check

The publishing review exercises one representative task and the skip destination in Playwright Chromium and WebKit at 1440, 720, 390 and 320px. Chromium additionally checks initial and task states with axe WCAG 2/2.1/2.2 A/AA rules and broad doubled-computed-text/forced-colors rendering. This is a scoped engine check, not the complete suite in Safari or a screen-reader session.
